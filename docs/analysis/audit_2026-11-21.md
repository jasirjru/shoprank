**Top model: the mean of the five DeBERTa-v3-base fold models.** The stack is 0.0006 higher but not

## 3. Can the numbers be trusted? (audit results)

**Leakage: none found.**
- Query text overlap train vs dev / dev2 / test: 0.00% exact, 0.00% after lower-casing and removing
  punctuation; 0.16-0.20% share the same word set (e.g. word order swapped). (query, product) pairs from
  train that reappear in test: 0.00%.
- 23.5% of test pairs use a product also seen in train. That is the official setup (same catalogue), not
  leakage. Does the model lean on it? On dev, DeBERTa scores 0.8825 on queries whose products were never seen
  in training, 0.8909 when 1-50% were seen, 0.8782 when over half were seen: flat. No sign of memorisation.
- Out-of-fold targets: folds by query, each train pair scored by the one fold model that never saw its query
  (checked in code). The served model's early stopping uses a train hold-out, never dev.
- Test discipline: pre-registered, scored once by `final_test.py`, guard file present. One crash (CUDA OOM)
  happened before any model score was written.

**Claims audit (independent reviewer agent): every test number, CI, paired difference, serving number and
ONNX number in README and model card matches its run record.** Wording errors found and fixed today:
1. "Models train on 80% of the official training queries; 20% held out" was wrong. dev+dev2 are 14.6%. Each
   DeBERTa fold trains on ~68% of the official training queries, the served MiniLM on ~77% (323,302 pairs).
   The model card's "285k-358k pairs" was wrong.
2. "+ brand and colour: -0.0002" had the wrong sign (the ablation removed them): +0.0002 (still nothing).
3. Model card: the distillation target is one fold model's score per pair, not the 5-model mean.
4. The 100-pair label audit was described as if representative. It is a sample chosen to find errors
   (most extreme disagreements), judged by an LLM reviewer and spot-checked; it does not estimate the label
   error rate. "Scores above ~0.90 are not realistic" was unsupported and is removed.
5. "Every number has a 95% CI" -> "every test number". "~2.6x slower" now says what is compared (5 DeBERTa
   models on GPU, 89 pairs/s, vs INT8 MiniLM on CPU, 230 pairs/s).
6. "Amazon's recipe (our run)" now says how it was adapted (bf16, length-bucketed batches, max length 128).

**Still unverified (by design or not yet done):** reproduction from a clean clone; CI has never run; the INT8
model has no test score (the test is spent; dev loss 0.0008); latency is from one laptop.

## 5. Behavioural robustness of the served model (dev, INT8)

Change the input in one controlled way, re-score all 2,001 dev queries, keep the labels. Predictions were
written in the notebook before the run.

| Perturbation | dev nDCG | change | Prediction |
|---|---|---|---|
| none | 0.8654 | | right |
| query in UPPER CASE | 0.8654 | 0.0000 | right (tokenizer lower-cases) |
| **one typo in the longest query word** | 0.8392 | **-0.0262** | wrong: worse than predicted |
| query words reversed | 0.8537 | -0.0117 | right |
| title only (brand, colour, bullets missing) | 0.8557 | -0.0097 | right |
| negation word deleted (158 negation queries) | slice 0.8347 -> 0.7585 | -0.0762 on the slice | **wrong**: predicted < 0.01 |

What it means:
- **Typos are the served model's biggest weakness.** One swapped letter pair costs 0.026 nDCG, more than
  distillation and bullets gained together. Real search traffic has many typos; a production team would
  fix this before anything else on the model side.
- **The model does read negation.** Deleting "without/not/no" changes the ranking a lot (within-query
  Spearman 0.50). So the earlier explanation "weak on negation because it ignores it" was wrong; the slice is
  weak for another reason (harder or noisier queries; not yet checked).
- Follow-up from the raw `shopping_queries_dataset_sources.csv`: 141 of the 158 dev negation queries come
  from ESCI's `negations` source (queries built on purpose to be hard). Their candidate lists are 31%
  Irrelevant vs 16% for other queries, with fewer Exact. DeBERTa on them: 0.850; on the 12 negation queries
  from the `other` source: 0.913 (too few for a firm claim). So the weak "negation" slice is mostly that
  hard query set, not negation itself. Source slices (DeBERTa / served): behavioral (62 q) 0.882 / 0.868,
  negations (141) 0.850 / 0.836, parse_pattern (181) 0.891 / 0.868, other (1,609) 0.891 / 0.870.
- Missing product fields cost ~0.01: callers should send brand, colour and bullets when they have them.
- Word order matters (-0.012), so the model is not a bag of words.

## 6. What a top professional would do here that the plan did not ask for

1. **Start from the product question.** Offline nDCG on judged lists is a proxy. A relevance team writes
   down who uses the ranker, which online metric it should move (click-through, add-to-cart, purchase), the
   latency budget, and the guardrails (zero-result rate, no worse than BM25 on any big slice) before modelling.
2. **Measure label noise on a random sample, not only on the model's disagreements.** Re-label ~200 random
   pairs by hand against the guidelines. That gives an error rate, a realistic ceiling, and lets you score the
   models on the cleaned subset. Our 75/100 number is from an error-hunting sample and cannot do this.
3. **Behavioural tests (CheckList style)** for typos, case, word order, missing fields and negation, with
   pass/fail thresholds, run in CI on every model change. Started today (section 5).
4. **A retrieval stage.** ESCI Task 1 hands you the candidates. A real system must find them in a catalogue
   of a million products; that is where most real failures are. Our two-tower stayed below BM25 (0.790 vs
   0.816 on dev).
5. **A launch plan:** shadow traffic, an A/B test with a power calculation (what lift is detectable at what
   traffic), monitoring for score drift and input drift, and a fallback to BM25 when the model is down or slow.
6. **A cost line:** cost per 1,000 queries for each option (CPU MiniLM vs GPU DeBERTa) next to the quality
   gap, so the business can choose.
7. **An external check of the whole repo:** a clean clone in a fresh machine and CI green, so that "it
   works" does not depend on this laptop.

4. **One targeted fix for the served model: typo robustness (section 5 found it is the largest weakness).**
   Distillation with typo augmentation: for a share of training pairs, put a typo into the query and keep the
   teacher's score for the *clean* query as the target, so the student learns that a typo should not change
   relevance. Judged on two numbers, both on dev: clean nDCG (must not drop by more than the seed spread)
   and typo nDCG (should recover most of the 0.026). One change, 3 seeds, ~10 min of GPU per seed, confirmed
   once on dev2. Pre-register first.
5. **Not recommended now:** DeBERTa-v3-large (does not fit 8 GB without big compromises; expected gain
   ~0.003-0.006 on the teacher only, and the served model barely moves), more stacking (measured: nothing),
   other locales (a new project, not a deeper one). A retrieval stage is the next *big* project, after the
   study block.
