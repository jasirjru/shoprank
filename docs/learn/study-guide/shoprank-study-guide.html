The big picture

The problem

A shopper types a query. The shop has millions of products. We must show the best products first. ShopRank builds this step by step and measures every step against labels written by humans.

  • Humans labelled every (query, product) pair with one of four labels:

1.2 Splits and leakage

Leakage = information from the evaluation data gets into training or tuning. Scores then look better than they will be on new data.

  • Why split by query, not by row: if "iphone xs pro" had 8 products in train and 8 in dev, the model learns "this query wants phones, not screen protectors" from train, and looks great on the same query in dev. Real users send new queries, so dev must have unseen queries.
  • How: 1 in 10 train queries go to dev, chosen by MD5(query_id) % 10 == 0. MD5 never changes, so the split is the same on every machine, every run.
  • BM25 statistics use product text only, never labels, so they are not leakage.

1.3 Ranking metrics: DCG and nDCG

A list is good when the best products are near the top. Position 1 matters most, and attention falls slowly as you go down.

DCG@k = Σi=1..k gaini / log2(i + 1)      nDCG@k = DCG@k / ideal DCG@k
  • Ideal DCG = DCG of the same gains sorted best-first. So nDCG is always between 0 and 1.
  • Why normalize: a query with 3 good products and one with 20 good products end up on the same 0 to 1 scale.
  • Why log: the discount grows slowly. Position 1 divides by 1, position 3 by 2, position 10 by 3.46.
Position i12345678910
log2(i+1)1.0001.5852.0002.3222.5852.8073.0003.1703.3223.459
Worked example (from the tests)

Ranked gains: [1.0, 0.1, 0.0, 0.01]

DCG@4 = 1.0/1 + 0.1/1.585 + 0/2 + 0.01/2.322 = 1 + 0.0631 + 0 + 0.0043 = 1.0674

Ideal order [1.0, 0.1, 0.01, 0.0]: 1 + 0.0631 + 0.005 + 0 = 1.0681  →  nDCG@4 = 1.0674 / 1.0681 = 0.99935

Only the last two swapped, and they barely matter. Order near the top matters most.

Other metrics: Recall@k = relevant products found in the top k ÷ all relevant products. Reciprocal rank = 1 ÷ position of the first relevant product. MRR = its average over queries.

Two nDCG versions here: nDCG@10 = what a shopper sees on page 1. nDCG full = over the whole candidate list, no cutoff. That is the official ESCI Task 1 metric (Amazon's trec_eval command with the same gains).

Notebook task 1.3

Ranked gains: [0.1, 1.0, 1.0, 0.0]. Compute DCG@4, ideal DCG@4 and nDCG@4. Use the log table above.

Answer 1.3

DCG = 0.1/1 + 1/1.585 + 1/2 + 0 = 0.1 + 0.631 + 0.5 = 1.231. Ideal [1, 1, 0.1, 0] = 1 + 0.631 + 0.05 = 1.681. nDCG = 0.732. Putting a Substitute first cost a lot, because position 1 has full weight.

1.4 Is a difference real? The paired bootstrap

System B beats A by 0.012 on 2,099 queries. With a different set of queries, could A have won? The bootstrap answers this without formulas.

deltas = b - a                                          # improvement per query
picks  = rng.integers(0, n, size=(10_000, n))           # 10,000 resamples WITH replacement
means  = deltas[picks].mean(axis=1)                     # mean improvement in each resample
low, high = np.percentile(means, [2.5, 97.5])           # middle 95% = confidence interval
  • Interval fully above 0 → B is better. Fully below 0 → A is better. Crosses 0 → no clear difference. Do not claim a win.
  • Paired: use per-query differences. Hard queries are hard for both systems, so subtracting cancels that out. The interval gets much narrower.
  • With replacement: some queries picked twice, some not at all. That imitates "a different sample of queries".
  • Fixed seed: the same interval every run.
Memorize

"+0.008 with 95% CI [−0.002, +0.018]" means not proven: the interval includes 0. Next step: more queries, check which query types gained, or call it no difference. Never ship it as an improvement.

1.5 BM25 — keyword search from the formula

Three ideas in one formula:

  1. Rare words matter more (IDF). "kindle" in 20 of 40,000 products says much more than "for".
  2. Repeats help, but less and less (saturation, set by k1). "case case case" is not 3× more about cases.
  3. Long texts get a penalty (length normalization, set by b). A 300-word listing matches many words by chance.
IDF(t) = ln(1 + (N − nt + 0.5) / (nt + 0.5))
score = Σt in query IDF(t) · f·(k1 + 1) / (f + k1·(1 − b + b·len/avglen))

N = number of products, nt = products containing word t, f = times t appears in this product, len = this product's length in words, avglen = average length. We used k1 = 1.5, b = 0.75.

  • Why the "1 +" inside ln: without it, a word found in more than half the products gets a negative IDF, so matching a common word would lower the score. Adding 1 keeps IDF ≥ 0.
  • b = 0 turns length penalty off. b = 1 is the full penalty. Our run: b = 0 was clearly worse (−0.0105).
  • BM25 has no idea of meaning: "sneakers" and "trainers" do not match; "phone" and "phone case" look alike.
Worked example

N = 40,000. "kindle" in 20 products: IDF = ln(1 + 39,980.5 / 20.5) = ln(1951.3) = 7.58. "for" in 30,000 products: IDF = ln(1 + 10,000.5 / 30,000.5) = ln(1.333) = 0.29.

Memorize · the leakage rule for features

Features may use query text and product text only, never the label. A test flips every label and checks no feature changes. Forbidden example: "how often this product was labelled Exact". That is the answer itself.

2.2 Logistic regression (the simplest learner)

It answers: "what is the probability this product is Exact?"

z = w1x1 + w2x2 + … + bias     p = σ(z) = 1 / (1 + e−z)

Sigmoid squeezes any number into 0 to 1. σ(0) = 0.5, σ(2) = 0.88, σ(−2) = 0.12.

Log loss (how wrong): for a true Exact product, −ln(p). Predict 0.9 → loss 0.105 (small). Predict 0.1 → loss 2.303 (big).

Memorize · the 4-step training loop (used by every model later, neural networks too) 
repeat:
  1. predict       p = sigmoid(X·w + b)
  2. loss          how wrong are we?  (log loss)
  3. gradient      which way to move each weight to lower the loss
  4. update        w = w − learning_rate × gradient      ("step downhill")
  • Standardize features (mean 0, standard deviation 1), so big-number features (title_len ≈ 20) don't drown small ones (coverage ≈ 0.5). Use the train mean and std for dev and test too.
  • L2 penalty = a small cost for big weights. It stops the model trusting one feature too much (less overfitting).
  • We wrote it from scratch in NumPy. It matched scikit-learn: weights equal within 0.0001, and both scored 0.8296 on dev.

2.3 Pointwise, pairwise, listwise

Looks atone product at a timethe whole list for a query
Learns"is this product Exact?""is this ORDER good?"

Analogy: pointwise = grading each student alone. Listwise = deciding the class ranking. Search needs a ranking, so listwise fits better. The three families: pointwise (score each item), pairwise (is A better than B?), listwise (optimize the whole list's metric). LambdaMART is pairwise/listwise.

2.4 LambdaMART (best model this week)

  1. MART = gradient-boosted decision trees. A tree asks yes/no questions ("coverage > 0.8? → brand_in_query = 1? → +0.3"). Boosting: tree 1, look at its mistakes, tree 2 fixes them, tree 3 fixes what is left. Final score = sum of all trees. Ours used 274 trees.
  2. Lambda = the ranking trick. For each pair of products in a query: "if I swapped these two, how much would nDCG change?" It pushes hardest on swaps that matter most (near the top, big label gap).
  • label_gain = [0, 0.01, 0.1, 1.0] tells LightGBM our ESCI gains. Its default (2label − 1) would optimize a different nDCG.
  • Early stopping: keep adding trees until a held-out 10% of train queries stops improving for 100 trees. We did not use dev for this; dev must stay a clean measurement.
  • learning_rate 0.05: each tree corrects only a little. Slower, but more reliable.
  • Trees are usually the strongest model for a small table of numbers, are fast, and don't need standardizing.

3.1 Autograd — how a network learns

A network has thousands to millions of weights. Training needs, for every weight, "if I nudge it up a little, does the loss go up or down, and by how much?" That is its gradient.

The trick: every number remembers how it was made. Then we walk backwards with the chain rule.

a = 2, b = -3
c = a * b        c remembers "a × b"
L = c + 10       L remembers "c + 10"

backward:  dL/dL = 1
           dL/dc = 1            (+ passes the gradient through)
           dL/da = b × 1 = -3   (× gives each input the OTHER input × gradient)
           dL/db = a × 1 =  2
OperationLocal rule (how the gradient flows back)
a + bboth get the gradient unchanged
a × ba gets b × grad, b gets a × grad
relu(a)passes the gradient if a > 0, blocks it (0) if a ≤ 0
exp(a)gets exp(a) × grad
log(a)gets (1/a) × grad
Memorize
  • Chain rule: the gradient along a path = product of the local slopes.
  • A value used twice: its gradients ADD. y = x·x + x → dy/dx = 2x + 1. The code uses +=.
  • Our engine matched PyTorch to 9 decimal places, and matched finite differences (nudge by 0.000001 and measure). loss.backward() in PyTorch is the same idea on big tables (tensors) on the GPU.

3.2 A neural network (MLP)

  • Neuron = weighted sum of inputs + bias, then ReLU = max(0, x) ("fire only if positive").
  • Layer = many neurons reading the same inputs. MLP = layers stacked: input → hidden → output.
  • Why ReLU (a non-linearity)? Without it, stacked layers collapse into one weighted sum, so the network only learns straight-line rules.
  • He initialization: start weights small and random, scaled by √(2 / inputs), so signals don't explode or vanish.
  • Training loop = the same 4 steps as week 2. New detail: set gradients to zero before each backward, because they add up. Forgetting zero_grad() is a classic bug.

3.3 The two-tower model

query text   ──► query tower   ──► 128 numbers ┐
                                                ├──► cosine similarity = relevance score
product text ──► product tower ──► 128 numbers ┘
  1. Text to ids (hashing trick): each word → one id for the word + one id per 3-letter piece. "anna" → word:anna, #an, ann, nna, na#. "ana" → word:ana, #an, ana, na#. They share 2 pieces, so misspellings still match. Pieces are hashed into 262,144 slots: no vocabulary file, new words still work.
  2. Tower: EmbeddingBag = one learnable 128-number vector per slot; a text = the average of its pieces. Then Linear → ReLU → Linear. Then normalize to length 1, so dot product = cosine similarity (−1 to 1).
  3. Why two towers: products are encoded once, ahead of time. At search time only the query is encoded, then compared with millions of stored product vectors very fast. This is how large-scale search works.

3.4 Contrastive learning — InfoNCE loss

Training data: 163,125 (query, Exact product) pairs. In a batch of 256 pairs, each query has 1 correct product and 255 other products in the batch that act as wrong answers: in-batch negatives, free, no extra labels.

             product1  product2  product3 ...
query1    [   HIGH      low       low   ]    want the diagonal high
query2    [   low       HIGH      low   ]
query3    [   low       low       HIGH  ]

Loss: for each row, softmax over the 256 similarities, then −log(probability of the correct one). This is just cross-entropy where the correct "class" is the matching product. Random guessing gives ln(256) = 5.545.

Temperature divides similarities before softmax:

Similarities [0.9, 0.5, 0.1]Softmax resultMeaning
temperature 0.05[0.9997, 0.0003, 0.0000]sharp, strong learning signal
temperature 1.0[0.472, 0.316, 0.212]almost flat, weak signal

False negatives: if the same query appears twice in a batch with two different Exact products, each is a correct answer for the other row. Punishing it teaches the wrong thing, so we mask those cells.

Memorize

InfoNCE = "pick the right partner out of the batch". In-batch negatives = other rows' positives. Temperature controls how sharp the softmax is. Mask false negatives.

  6. Train on one small batch many times; it should reach ~0 loss. Ours stopped at 0.37 because 41 rows had duplicate product text.

What comes next — weeks 4 to 10

Read for understanding, not memory. Each week fixes a failure you already saw.

Week 4 — Transformers, tokenization, dense retrieval, ANN

Attention(Q, K, V) = softmax(Q·KT / √d) · V
  • Each word asks a query (Q), compares it with every word's key (K), and takes a weighted mix of their values (V). So "case for iphone" and "iphone for case" differ: words see their context.
  • Divide by √d (d = vector size, e.g. √64 = 8) so dot products don't grow huge and make softmax too sharp.
  • Cost grows with length² (every word looks at every word).
  • Tokenization (WordPiece/BPE): rare words split into pieces. Watch model numbers like "sm-g991b".
  • Sentence-BERT: a pretrained transformer that gives one vector per text (often the mean of word vectors).
  • HNSW (FAISS): a graph of products. Search jumps between near neighbours instead of comparing with all million products. Trade-off: recall vs speed, set by M and efSearch. Target: recall@100 ≥ 0.98 vs exact search.

Week 5 — Fine-tune the bi-encoder; hybrid search

  • Hard negatives: wrong products that look right, mined with BM25. Never use labelled E or S products as negatives (they would be false negatives).
  • Fusion: combine BM25 and dense results. RRF score = Σ 1/(60 + rank). A product ranked 1st in A and 3rd in B: 1/61 + 1/63 = 0.0323.
  • Mixed precision (fp16) for speed; watch for overflow (NaN loss).

Week 6 — Cross-encoder reranker

  • A cross-encoder reads query and product together, with full attention across both. Much more accurate, much slower. So use it only on the top 50.
  • Bi-encoder = fast, precomputed, good for finding candidates. Cross-encoder = slow, accurate, good for final order.
  • Error taxonomy on 200 failures: substitute vs exact, brand, colour, negation, numbers, size units.

Week 7 — Small LLM query parser with QLoRA

  • Turn "air force 1 shoes girls" into JSON: {"brand": "nike", "gender": "girls", ...}.
  • LoRA: freeze the big weight W; learn two small matrices A (d×r) and B (r×d); new weight = W + B·A. Parameters for rank 16 on a 2048×2048 layer: 16 × (2048 + 2048) = 65,536 instead of 4,194,304.
  • QLoRA: the frozen base model is stored in 4-bit (NF4), so a 1.5B model fits on an 8 GB GPU.
  • Treat LLM output as untrusted: validate the JSON.

Week 8 — Fast serving

  • Export the reranker to ONNX, quantize to int8: faster on CPU, check how much nDCG drops.
  • FastAPI /search, Postgres catalogue, cache, load test. Report p50 / p95 / p99 latency. Target: p95 < 300 ms on CPU.

Week 9 — MLOps

  • Docker, GitHub Actions with an eval gate: if nDCG on a smoke set drops more than 0.01, the build fails.
  • MLflow for runs and models. Monitor drift without labels: compare input distributions (PSI), score distributions.
  • Training/serving skew: features computed differently online and offline.

Interview questions

Say each answer out loud, then write the key words in your notebook. A strong answer uses your own numbers and names failures without being asked.

1. Walk me through your ranking pipeline. Cheap stages on many products, expensive stages on few: BM25 + dense find ~200 candidates fast; LambdaMART on features narrows to 50; a cross-encoder orders the top 10. Each stage fits a time budget.
2. Your nDCG improved by 0.02. Is it real? I check with a paired bootstrap over queries: 10,000 resamples of per-query differences, 95% interval. If it excludes 0, it is unlikely to be luck. I also check per query type, because a gain can come from one segment.
3. Why split by query? Rows of the same query in train and dev let the model memorize the query. Real traffic brings new queries.
4. Why LightGBM before a neural reranker? It is cheap per product, works great on a small table of features, is easy to explain (feature importance), and it gave +0.0166 over BM25 with a clear interval.
5. Pointwise vs listwise? Pointwise predicts each item alone; listwise optimizes the order (nDCG). In ShopRank listwise won by +0.0062 [+0.0032, +0.0093].
6. Your neural model lost to BM25. Why? No pretrained language knowledge; easy in-batch negatives while Task 1 lists are all on-topic; bag of pieces ignores word order. Fixes: pretrained transformer, hard negatives, attention.
7. Why do hard negatives help, and when do they hurt? They teach the fine differences the test needs. They hurt when a "negative" is actually relevant (unlabelled, or labelled S/E): a false negative trains the wrong lesson.
8. What is inside LoRA? Parameters for rank 16 on 2048×2048? Freeze W, learn W + B·A with small A and B. r × (din + dout) = 65,536 instead of 4.19 million.
9. How do you detect drift without labels? Watch input distributions (query length, language, PSI on features), score distributions, and proxy metrics like click rate.
10. What would you not trust in your own results? Label noise (e.g. Exact = batteries for an IQOS query), US-only vs 3-language public numbers, and offline-only evaluation without real users.
11. Why nDCG, not accuracy? Order matters and users look at the top; nDCG rewards good items high up and handles graded labels.
12. Explain BM25 in three ideas. Rare words count more (IDF), repeats saturate (k1), long texts are penalized (b).

Glossary and final self-test

Baseline: the simple system you must beat.

Leakage: evaluation information gets into training or tuning.

Dev / test: dev for tuning; test locked until the end.

Gain: the number value of a label (E = 1.0).

Confidence interval: range where the true improvement probably lies.

Feature: one number describing a query-product pair.

Weight: how much the model trusts a feature.

Loss: how wrong the model is.

Gradient: which way to move weights to lower the loss.

Learning rate: size of each step.

Overfitting: memorizing train; bad on new data.

Regularization (L2): penalty that keeps weights small.

Boosting: each new tree fixes earlier trees' mistakes.

Early stopping: stop when held-out score stops improving.

Embedding / vector: list of numbers that stands for a text.

Negative: a wrong answer used in training.

Temperature: sharpness knob for softmax.

Epoch: one pass over all training data.
